# D-010 Kafka producer, consumer, offsets and dead letters

**Status:** decided by the agent, Phase 1, except the dead-letter topic itself, which needs approval (D-012).

- **Producer:** plain `KafkaProducer` behind a bounded in-memory queue (D-004) drained by one sender thread. `acks=all`, idempotence on, `delivery.timeout.ms=60000`, `max.block.ms=2000`.
- **Acknowledgement semantics:** the HTTP API answers `202` only after the broker acknowledges the record, waiting up to 5 s. If the queue is full it answers `503` with `Retry-After` at once. If the broker does not acknowledge in 5 s it answers `503`; the record may still be delivered later, and a client retry is harmless because storage deduplicates on the natural key (D-009). A record that exhausts `delivery.timeout.ms` is logged with its `eventId` and counted `asset_ingest_dropped_total{reason=delivery_timeout}`. Nothing is dropped without a log line and a counter. A pod crash loses queued, unacknowledged records; their clients never got a 202.
- **Consumer:** group `asset-service`, channel `telemetry-in` on `box1.telemetry.events.v1`, ordered blocking processing. It ignores `equipment.threshold-exceeded.v1` records (its own output) and unknown event types without error.
- **First start offset policy:** `auto.offset.reset=latest`. Readings are perishable, nothing consumes the topic today, and replaying up to 48 h of someone else's readings on first start would create alerts for stale data. After the first start, committed offsets carry over restarts. If the group's offsets are lost, it resumes from `latest` and the gap is visible as missing readings, not as false alerts. Documented in the runbook with the `kafka-consumer-groups --reset-offsets` command for a deliberate replay.
- **Poison records:** records that are not valid JSON, fail the envelope or payload schema, or fail service validation go to `box1.telemetry.dlq.v1` via the SmallRye dead-letter strategy, with headers carrying the reason code only (no driver text, order-run lesson). Valid records hit by a database outage are never dead-lettered: they retry with backoff and hold the partition (inventory-run lesson).
- **Readiness:** PostgreSQL is a readiness dependency; Kafka is not (an outage is visible as backpressure and lag, not as a pod restart loop).
